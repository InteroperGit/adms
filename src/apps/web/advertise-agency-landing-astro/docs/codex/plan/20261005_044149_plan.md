# Hot offers carousel

**Status:** In progress; task 017 completed, tasks 017a and 018–021 pending.

## Goal and placement

Add a compact «Горячие предложения» carousel to the homepage immediately below the header and above About. Each offer contains an image, a short description and a clearly named link button. Provide previous/next arrows, circular position indicators with a selected current dot, and automatic slide changes. Preserve the visually hidden homepage h1, existing sections and navigation, butterfly branding, theme settings and cookie behavior.

Use an Astro component with a small browser script and existing design tokens. No React or carousel dependency is needed. Apply frontend-design, astro-best-practices and Playwright during implementation; consult the Astro component, styling and content guides from [AGENTS](../../../AGENTS.md). Follow [task management](../task-management.md).

## Content and configuration

Store settings and offers in `data/content/offers.json`, with validation and a typed export following the project's existing content wrappers. Include `enabled`, `autoplay`, `intervalMs` (default 7000, validated minimum 5000), section title, and an ordered `items` array. Each item needs a stable unique `id`, `title`, `description`, `image`, `imageAlt`, `imageWidth`, `imageHeight`, `linkLabel`, `href` and `enabled`. Validate positive dimensions, nonempty text, unique IDs and internal or HTTP(S) links; reject unsafe schemes.

Image paths should normally reference approved local files under `public/images/offers/`. Provide meaningful alt text or empty alt for an image that is purely decorative. Do not invent discounts, prices, deadlines, client results or offer eligibility. Missing promotional copy/artwork is an agency input. Existing service copy may be used only as clearly identified preview content; leave production publication disabled until real offers are supplied. Never present arbitrary stock/project placeholders as proof of a promotion.

Use explicit ordering and per-item enable switches rather than hidden sorting. No scheduling, countdowns, tracking or inquiry form is required in this first version.

## Component and visual design

Create `src/components/sections/OffersCarousel.astro`; keep data separate from presentation. Extract a slide component only if it improves readability. Render only on `/`.

- Desktop: balanced image/text composition, restrained offer title, short copy and one CTA. Mobile: image above copy, controls below content so arrows do not obscure text or buttons. Keep the carousel compact enough to introduce the agency without pushing the next section excessively down the page.
- Match the current orange/blue identity and semantic Light/Dark surfaces. Use a visible section heading and offer headings below it in the hierarchy; do not create a second h1. Reserve image dimensions/aspect ratio and avoid changing carousel height during rotation. Accommodate the longest supplied copy through responsive layout, without truncation or hard heights that clip enlarged text.
- Put left/right arrow buttons, circular dots and a pause/play control in a coherent control row. Use local SVGs and clear Russian accessible names. Highlight the current dot with shape/border as well as color; optionally show a quiet «1 / 3» counter for extra orientation. Keep small visible dots inside generous click targets, at least 44×44px for interactive controls.
- Clicking a dot selects its slide; arrows cycle through the ordered list and wrap from last to first. Do not open slide links when arrows/dots are used. Avoid whole-slide click handlers; use a real anchor CTA. Keep tab destinations within the current slide only.
- Add subtle transitions that respect reduced motion. Avoid animated zoom, parallax, flashing captions or continuous progress bars. Image errors must retain reserved geometry and leave copy/CTA readable.

## Rotation and interaction

Use one timer per carousel with clear start/stop logic. Autoplay starts only when configured, more than one item exists, the carousel is visible in the viewport, the document is visible, and reduced motion is off.

Pause on pointer hover, keyboard focus within the carousel, hidden tab, and when the carousel leaves the viewport. Provide an explicit pause/play button; a user pause persists for the current page visit. After keyboard interaction or manual slide selection, stop automatic rotation until the user explicitly presses Play. Do not restart simply because focus or pointer leaves. Explicit Play still respects focus/hover/visibility/reduced-motion constraints; explain this behavior in the implementation documentation.

Auto-rotation never moves focus or announces each change. Manual changes may update a concise polite status («Предложение 2 из 3»); keep automated changes silent. Do not replace a focused CTA automatically. Optional touch swipe is valuable if it remains a small implementation: horizontal gestures only, threshold and direction checks, preserve vertical scrolling, and suppress accidental CTA activation after a swipe. Buttons remain the primary alternative. Avoid document-wide arrow-key interception; native Tab/Enter/Space must suffice.

## Accessibility and edge cases

Use a named region with carousel semantics, labeled slides and native controls. Dots expose the selected position consistently (for example `aria-current="true"`); do not apply tablist semantics unless the full tabs keyboard pattern is implemented. Hidden slides must be absent from the accessibility tree and tab order. Retain visible focus and text/icon contrast (4.5:1 normal text, 3:1 essential icons/controls).

- Disabled carousel or zero enabled items: omit the section and its controls.
- One enabled item: render a static offer without arrows, dots or autoplay controls.
- Multiple items without JavaScript: show offers as a readable stacked list with working CTA links; hide inactive JS controls. Enhance only after successful initialization so visitors do not lose content if scripts fail.
- Reduced motion: default to paused, no slide animation. User may navigate manually. Preserve readable content if storage or external assets fail; autoplay needs no storage or cookies.
- First visible image may be eager-loaded; remaining images load lazily or on approach to their slide. Avoid eager loading every offer or adding build-time downloads. Set priority only if this image is actually the likely LCP asset; measure rather than assume.
