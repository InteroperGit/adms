# Спецификация API сервиса отправки данных форм заказа

Статус: draft, версия 1.0

Документ описывает backend-сервис, который принимает заявки с сайта агентства,
надёжно ставит их в очередь доставки и возвращает браузеру подтверждение приёма.
Сервис не должен считать заявку принятой только потому, что HTTP-запрос был
разобран или обработчик завершился без исключения.

## 1. Границы и цели

Сервис должен:

- принимать заявки главной формы и специализированной формы световых букв;
- проверять структуру, типы, длины, обязательность и допустимые значения;
- защищать endpoint от повторов, подделки источника, ботов и перегрузки;
- атомарно сохранять заявку или ставить её в устойчивую очередь;
- доставлять заявку в одобренный канал агентства;
- возвращать стабильный идентификатор приёма для повторных запросов.

Сервис не должен принимать секреты, HTML-шаблоны или произвольные поля от
браузера. Адрес получателя, ключи провайдера, правила хранения и параметры
лимитов размещаются только в конфигурации backend-среды.

## 2. HTTP-интерфейс

| Параметр        | Требование                                         |
| --------------- | -------------------------------------------------- |
| Метод           | `POST`                                             |
| Путь            | `/v1/order-inquiries`                              |
| Content-Type    | `application/json; charset=utf-8`                  |
| Аутентификация  | браузерный endpoint без пользовательского токена   |
| Credentials     | не принимает cookies и HTTP-редиректы              |
| Размер тела     | не более 16 KiB до разбора JSON                    |
| Таймаут клиента | значение из конфигурации формы, обычно 15 секунд   |
| CORS            | только точные production-источники из конфигурации |

Если deployment использует другой путь, он задаётся в
`data/content/config/order-inquiry.json`. Путь должен оставаться локальным или
быть credential-free HTTPS URL. Сервис обязан отвечать JSON даже при ошибке.

## 3. Общий формат заявки

Все значения полей передаются строками. Пробелы по краям удаляются после
проверки типа. Неизвестные поля отклоняются, а исходный payload не записывается
в логи.

Общие поля:

| Поле        | Обяз.                 | Ограничение                            |
| ----------- | --------------------- | -------------------------------------- |
| `name`      | да                    | 1–120 символов                         |
| `email`     | для главной формы да  | до 254 символов, RFC-подобная проверка |
| `phone`     | для главной формы нет | до 40 символов, 7–15 цифр              |
| `message`   | для главной формы да  | до 5000 символов                       |
| `consent`   | да                    | ровно строка `on`                      |
| `requestId` | да                    | UUID v4                                |

Пример заявки главной формы:

```json
{
  "name": "Анна Петрова",
  "email": "anna@example.com",
  "phone": "+7 900 123-45-67",
  "message": "Нужна вывеска для магазина, монтаж в июне.",
  "consent": "on",
  "requestId": "4f7c2b2f-4d7b-4a9e-9d6d-31c5dce0a1af"
}
```

## 4. Специализированная форма световых букв

Наличие `serviceId` или `projectId` выбирает специализированный контракт. Помимо
общих полей сервис принимает:

| Поле             | Обяз. | Допустимые значения или лимит                       |
| ---------------- | ----- | --------------------------------------------------- |
| `company`        | нет   | до 120 символов                                     |
| `signText`       | нет   | до 300 символов                                     |
| `address`        | нет   | до 300 символов                                     |
| `facade`         | нет   | до 300 символов                                     |
| `fileLink`       | нет   | до 2000 символов, только HTTP(S) без учётных данных |
| `widthCm`        | нет   | положительное число, до 100 символов                |
| `letterHeightCm` | нет   | положительное число, до 100 символов                |
| `budget`         | нет   | положительное число, до 100 символов                |
| `deadline`       | нет   | дата `YYYY-MM-DD`                                   |
| `lighting`       | да    | `advice`, `front`, `halo`, `combined`               |
| `installation`   | да    | `advice`, `yes`, `no`                               |
| `power`          | да    | `unknown`, `available`, `needed`                    |
| `contactMethod`  | да    | `phone` или `email`                                 |
| `serviceId`      | да    | `svetovye-bukvy`                                    |
| `projectId`      | нет   | идентификатор опубликованного проекта               |

Для этой формы обязательны `name` и `phone`. Если `contactMethod` равен `email`,
дополнительно обязателен корректный `email`. Список `projectId` сверяется с
доверенным опубликованным каталогом сервиса, а не с данными клиента.

## 5. Успешный ответ и идемпотентность

При устойчивом сохранении или постановке в очередь сервис возвращает:

```http
HTTP/1.1 202 Accepted
Content-Type: application/json; charset=utf-8
```

```json
{
  "accepted": true,
  "receiptId": "inq_01J9ZQ7J3Q7V5N7E0M2V6QK8P4"
}
```

`receiptId` — непрозрачная непустая строка, не содержащая персональные данные.
Клиент очищает форму только при `accepted: true` и непустом `receiptId`.

`requestId` является ключом идемпотентности. Для того же `requestId` и
идентичного payload сервис возвращает тот же `receiptId`, в том числе после
перезапуска. Проверка и сохранение ключа выполняются атомарно. Если тот же
`requestId` пришёл с другим payload, сервис отвечает `409` и не создаёт новую
заявку. Гонка двух одинаковых запросов не должна создавать две доставки.

## 6. Ошибки

Формат ошибки:

```json
{
  "accepted": false,
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "Проверьте данные формы.",
    "fields": ["email", "consent"]
  }
}
```

Публичное `message` не раскрывает внутренние причины, адреса получателей,
трассировки или персональные данные.

| HTTP | `code`                   | Когда использовать                         |
| ---- | ------------------------ | ------------------------------------------ |
| 400  | `INVALID_JSON`           | тело не является JSON-объектом             |
| 400  | `VALIDATION_ERROR`       | поле отсутствует, неверно или неизвестно   |
| 403  | `ORIGIN_FORBIDDEN`       | источник не разрешён политикой CORS/origin |
| 409  | `IDEMPOTENCY_CONFLICT`   | `requestId` повторён с другим payload      |
| 413  | `PAYLOAD_TOO_LARGE`      | превышен размер тела                       |
| 415  | `UNSUPPORTED_MEDIA_TYPE` | не JSON                                    |
| 429  | `RATE_LIMITED`           | превышен лимит запросов                    |
| 503  | `DELIVERY_UNAVAILABLE`   | очередь или провайдер временно недоступны  |
| 500  | `INTERNAL_ERROR`         | непредвиденная ошибка без утечки деталей   |

Временные ошибки не подтверждают приём. Браузер сохраняет введённые данные и
может повторить запрос с тем же `requestId`.

## 7. Безопасность и защита от злоупотреблений

- Разрешить только `POST`, JSON и настроенные production origins.
- Отключить cookies, credentials и автоматические redirects.
- Ограничить тело, частоту запросов по IP и, при наличии, по fingerprint.
- Применить CAPTCHA или другой одобренный bot challenge при подозрительном
  трафике; токен challenge не заменяет проверку полей.
- Отбрасывать управляющие символы, заголовочные инъекции и неизвестные поля.
- Экранировать весь пользовательский текст перед письмом или HTML.
- Не подставлять пользовательский текст в email-заголовки и SQL/шаблоны.
- Не скачивать `fileLink` в рамках обработки заявки.
- Хранить секреты, журналы и персональные данные по утверждённой политике.

## 8. Доставка и наблюдаемость

Сначала сервис фиксирует нормализованные поля и статус `accepted` в устойчивом
хранилище или очереди, затем выполняет доставку. Повторная доставка должна быть
безопасной и связанной с тем же `receiptId`. Для каждой заявки нужны технические
метрики `accepted`, `rejected`, `queued`, `delivered`, `failed`, `duplicate` и
latency; значения полей и email в логах запрещены.

Алерт должен срабатывать при росте `5xx`, отказах очереди, переполнении лимитов
и длительной задержке доставки. Оператор должен уметь найти заявку по
`receiptId` и `requestId`, не раскрывая её содержимое в обычном логе.

## 9. Конфигурация и включение

До утверждения получателя, текста согласия, провайдера и retention-политики:

1. оставить `submission.enabled: false` и пустой endpoint;
2. развернуть сервис в тестовом окружении с перехватом доставки;
3. проверить реальные origin, лимиты, очередь, повторы и отказ провайдера;
4. выполнить контролируемую заявку и подтвердить получение агентством;
5. только после этого включить endpoint в content-конфигурации и выпустить сайт.

Откат выполняется отключением приёма на backend и `submission.enabled: false` с
последующей пересборкой сайта. Уже принятые элементы очереди обрабатываются по
согласованной процедуре хранения или удаления.

## 10. Критерии приёмки

- Валидные payloads обеих форм получают `202`, `accepted: true` и receipt.
- Невалидные, лишние и слишком длинные поля получают предсказуемую ошибку.
- Повтор того же payload не создаёт вторую доставку и возвращает тот же receipt.
- Конфликт payloads с одним `requestId` получает `409`.
- Перезапуск сервиса не теряет ключи идемпотентности и принятые заявки.
- Отказ очереди не выдаёт ложное подтверждение и не очищает форму клиента.
- CORS, rate limit, body limit и bot protection проверены в staging.
- Секреты отсутствуют в репозитории, JSON-контенте и браузерном bundle.
- Тест подтверждённого получения выполнен с реальным согласованным каналом.
